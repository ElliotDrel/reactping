# ReactPing

Bot DMs when someone reacts to your Slack messages, with an optional single inbox across connected workspaces.

Status (November 13, 2026): the website and Node.js API are deployed at [reactping.vercel.app](https://reactping.vercel.app), connected to Supabase Postgres. Hosted health, API routing, TLS certificate verification, private-table RLS/grants, and empty-queue delivery checks pass. Public signups, Slack installs, and indexing remain disabled. **Email-code sign-in is blocked on custom SMTP:** this free project rejects changes to the default magic-link template. No Slack behavior has been tested on this hosted version. See [the connection guide](docs/connection-guide.md), [setup](docs/setup.md), and [verification](docs/verification.md). Superseded: the previous locally checked, not-deployed status; historical SQLite Slack results do not cover this code.

## V1

- Authorize each source workspace with user-level `reactions:read`.
- Select one connected workspace as the destination, or deliver within each source workspace.
- Notify only when `item.type` is `message`, `item_user` matches a connected user in that workspace, and the reactor is someone else.
- Send the reaction, source workspace, and a link to the original message. No message excerpts, history ingestion, or content storage. Disable link/media unfurls.
- Link workspace identities to a signed-in account through one-time, browser-bound OAuth state; never infer account ownership from matching display names or email addresses.
- Provide disconnect and deletion of stored credentials.

Each workspace requires authorization under its own app policies. Connecting a source to another workspace exports reaction metadata, even without message text: make routing explicit and default to same-workspace delivery.

## Architecture

One repository, TypeScript on Node 24, deployed to Vercel with Supabase for Postgres and Auth. Superseded: the `node:http` service, SQLite file, in-process timer, and Docker image.

- **Website:** static HTML generated by `scripts/build.ts` from reusable layouts in `site/`, plain CSS, and two small vanilla TypeScript bundles built with esbuild (`site/client/site.ts` for navigation; `site/client/app.ts` for `/app`, using the pinned `@supabase/supabase-js` browser client). Routes: `/`, `/features`, `/install`, `/faq` (with `#support`), `/about`, `/privacy`, `/terms`, `/app`.
- **API:** one Vercel Node.js function serves every `/api/*` path (`src/vercel.ts` → `src/api.ts`, Web `Request`/`Response`). `npm run dev` (`src/dev.ts`) runs the same handler locally beside the built static files.
- **Build output:** `npm run build` writes Vercel Build Output API v3 to `.vercel/output` (static files, `functions/api.func`, and `config.json` routes: security headers, clean URLs, `/api/*` catch-all, 404). `vercel.json` only names the install and build commands; routing lives in the generated, tested `config.json`.
- **Accounts:** Supabase Auth email one-time codes; no passwords. The browser sends its Supabase access token as a bearer token, and the API verifies it with Supabase Auth (`GET /auth/v1/user`) using only the publishable key. Public sign-up needs custom SMTP in Supabase; the built-in sender is for testing.
- **Slack install:** a separate OAuth flow started by a signed-in user. The API stores a hashed one-time state (10 minutes) bound to the user and to a random secret in an HttpOnly, `SameSite=Lax`, `__Host-` cookie; the callback must present both. Installs start only from the canonical `PUBLIC_SITE_URL` origin.
- **Database:** Supabase Postgres through `pg` and `DATABASE_URL`. All tables live in the private `reactping` schema with RLS enabled, no policies, and every privilege revoked from `anon`/`authenticated` (`supabase/migrations/`). No Supabase secret or service-role key is used anywhere.
- **Delivery:** Slack events are verified, filtered, and written to the Postgres outbox before the `200`. Delivery is attempted right away in `waitUntil`, and `POST /api/internal/deliver`, authenticated by its own `DELIVERY_CRON_SECRET`, is called every minute by Supabase `pg_cron` + `pg_net` with secrets in Vault (`supabase/cron.template.sql`). No always-on process or Vercel cron is needed.

Stored: encrypted installation credentials (AES-256-GCM), linked workspace/user IDs, routing preferences and consent time, and 48-hour minimal event/delivery records. Each delivery is claimed with `for update skip locked` and a 60-second lease, so concurrent invocations never hold the same row and a crashed attempt is retried after the lease expires. Deduplicate by Slack event ID and recipient, retry transient failures with persisted backoff, persist Slack rate-limit pauses for every instance, recheck authorization and consent before posting, and surface revoked credentials. Do not promise exactly-once delivery after an ambiguous Slack API timeout or a crash mid-send.

Start with user `reactions:read` and bot `chat:write`. Resolve original-message links with the source user's token. Prefer source user mentions for same-workspace alerts; use a neutral actor label across workspaces. Add no history scopes for previews.

## Shipping sequence

1. Superseded (done on the v1 SQLite service, October 2026): real reaction DMs in a public channel, from Elliot and from a second person. Private channels, threads, DMs, group DMs, Slack Connect, and cross-workspace routing remain unverified.
2. Done locally: website, Supabase-backed accounts, workspace linking, destination choice, connection test DM, disconnect, account deletion, Postgres outbox with leases, and secret-safe build.
3. Connected: Supabase schema/Auth configuration and Vercel production runtime; Vault-backed delivery recovery is configured. Next: configure custom SMTP and verify email-code sign-in, settle the final domain/support contact, then configure Slack URLs only when live Slack testing is authorized.
4. Keep the deployed app closed until the hosted pilot is authorized and verified, then turn on `REACTPING_INSTALLS_ENABLED` and `PUBLIC_INSTALL_ENABLED`. Tag v0.1.0 after the hosted pilot passes.

Ship criterion: a hosted pilot works end to end for Elliot across two workspaces with documented coverage and no message-content collection. Public distribution and Marketplace submission are subsequent releases; this repository stays private until Elliot requests otherwise.

## Development

Requires Node 24+ and, for the database tests, Docker.

```sh
npm ci
npm run db:test:start                 # disposable Postgres on 127.0.0.1:54329
export TEST_DATABASE_URL=postgres://postgres:postgres@127.0.0.1:54329/postgres
npm run check                         # format:check, typecheck, lint, build, test
npm run db:test:stop
npm run format                        # prettier --write
npm run dev                           # build, then serve site + API on PORT (default 3000) with .env if present
```

Without `TEST_DATABASE_URL`, Postgres-backed suites are reported as skipped; the build, configuration, Slack client, and encryption tests still run. Without any `.env`, `npm run dev` serves the full site, `/app` shows "Setup not connected", and every API route except `/api/health` returns `503 not_configured`. Normal behavior excludes your own reactions; set `INCLUDE_SELF_REACTIONS=true` only for solo testing (the app shows a testing notice).

Layout: `site/` (pages, layout, styles, browser code), `scripts/build.ts` (static + Vercel output), `src/api.ts` (routes, auth, OAuth, events), `src/delivery.ts` (outbox worker), `src/db.ts` (Postgres store), `src/events.ts` (signature check, filtering), `src/slack.ts` (Slack client and error mapping), `supabase/` (migration and cron template). Tests live in `test/`; see [test migration](docs/test-migration.md) for how the v1 tests map to the new ones.

Environment contract: [`.env.example`](.env.example). URLs under `PUBLIC_SITE_URL`: Slack OAuth redirect `/api/slack/oauth/callback`, Slack events `/api/slack/events`, cron target `/api/internal/deliver`.
